GTEAM LANGUAGE - DRAFT

GTL

GTeam Language is a multi-purpose programming language designed for GTeam OS, microcontrollers, hardware, system software, and general applications.

GTeam OS Run .gtl programs directly through the planned GTeam OS environment.
Hardware Control GPIO, SPI, I²C, displays and other hardware through GTeam libraries.
Low-level Designed to reach system-level code while remaining useful for normal applications.

What is GTL?

GTL stands for GTeam Language. It is intended to become a language that can span multiple layers of the GTeam ecosystem.

Instead of having one language for applications, another for microcontrollers, and another for system software, GTL aims to provide a common language for all of them.

Core idea: One GTeam language that can control hardware, create applications, run on GTeam OS, and eventually be used for parts of the operating system itself.
GTL │ ├── Microcontrollers │ ├── GTeam OS │ ├── Hardware │ ├── Applications │ └── System Software

File Format

Extension Purpose
.gtl GTL source code

GTeam OS is intended to support running .gtl source directly from its source-code environment. (GTL Apps, Not Normal GTL. This is to prevent user and developers from accessing low-level stuff.)

Basic Syntax

Comments

GTL uses >> and << for comments. 

>> Single-line comment <<
>>
Multi-line comment
Multiple lines can be placed here.
<<

Output

The basic output function is output(). 

output("Hello, world!")
output(var "name")

Variables

Variables are created and modified using the var system.

Creating a variable

var make "name"

Setting a variable

var set str "name" = "GTeam"
var set val "count" = 0

Changing a value

var cal add "count", 1

Reading a variable

output(var "count")

Constants

const PI = 3.14159

Conditions

If

if var "x" > 10 then
    output("Big")
end

Else

if var "x" > 10 then
    output("Big")
else do
    output("Small")
end

Else-if

if var "x" > 10 then
    output("Big")
else if var "x" == 10 then
    output("Exactly 10")
else do
    output("Small")
end

Loops

Forever Loop

repuntil repeats while its stopping condition remains false. 

repuntil False do
    output("Running...")
end

Conditional Loop

repuntil var "x" > 10 do
    var cal add "x", 1
end

For Loops

GTL will support a dedicated iteration syntax for counted and collection-based loops. The exact grammar remains part of the language draft.

Functions

Functions allow reusable pieces of code to be defined and called. 

def add(a, b) func
    return cal add a, b
end

The final grammar may simplify the function declaration syntax while retaining the same concept.

Arrays & Lists

Creating a list

list set "numbers" = [1, 2, 3, 4]

Accessing an element

output(list get 0 "numbers")

Structs & Objects

User-defined structures are a possible part of GTL's type system. They can represent related data as one object. 

struct Player {
    name: string
    health: int
}

The exact object syntax is still under development.

Memory

Memory management is especially important because GTL is intended to run on both ordinary computers and constrained microcontrollers.

General model

Normal GTL programs should not need to manually manage every allocation. GTL can provide automatic memory handling while still exposing lower-level controls where required.

Checking memory

var set bool "mem_available" =
    memory.checkava(1048576)

Reserving memory

if var "mem_available" then
    memory.reserve(1048576)
else do
    skip
end

Freeing memory

memory.free(area)

Smart memory

uselib smartmem as sm

sm.collect()
Normal application code should not need to manually reserve storage just to read a normal file. Filesystem operations should handle storage internally, while applications may reserve memory for buffers when necessary.

Hardware

Hardware support is one of GTL's defining features. Hardware APIs are intended to be provided through GTeam libraries.

Libraries

uselib gteamtools as gt

GPIO

mt.gpio.send(5, True)

SPI

mt.spi.send(...)

I²C

mt.i2c.send(...)

Example library structure

uselib gteamtools as gt
uselib gt.mcutools as mt
uselib mt.tftdisplaytools as tft
GTL hardware APIs are intended to provide a consistent interface across supported GTeam hardware and devices.

Errors

GTL's final error-handling system has not yet been finalized.

Possible models include structured exception handling: 

try {
    ...
} catch error {
    ...
}

Or result-based error handling: 

result = function()

if result.error then
    ...
end
The final system should be predictable and suitable for both application developers and low-level firmware.

Concurrency

Program execution and concurrency should be treated as separate concepts.

Running another GTL file is not automatically the same thing as creating a concurrent task. 

run("program.gtl")

A future task or scheduler system can provide actual concurrency. A central system component can control task execution.

Kernel Mode

GTL is intended to eventually support system-level programming for GTeam OS.

Possible low-level APIs include:

memory.map(...)

interrupt.register(...)

Kernel Entry Point

code kernel_main() do

Kernel Arguments

Booting

GTL does not need to replace BIOS or UEFI firmware. Existing firmware can load a small C-based environment which starts the GTL system.

BIOS / UEFI ↓ Tiny C-based GTL OS ↓ SC/ ├── program1.gtl ├── program2.gtl ├── system.gtl └── ... ↓ GTL Syntax Checker ↓ GTL Converter ↓ Execution

The source-code files are intended to be stored in an SC folder inside the bootable image.

The C component is intended to provide the tiny underlying environment needed to boot and execute the GTL system. It is not intended to become the main GTL programming environment.

GTL Runtime

The GTL runtime is the environment responsible for processing GTL source code and providing the functionality required to execute it.

Potential responsibilities

  • Reading GTL source files
  • Checking GTL syntax
  • Converting GTL source into an executable form
  • Memory management
  • I/O
  • Hardware abstraction
  • Standard library support

The exact runtime architecture remains under development.

Compilation

GTL is designed around a source-code-oriented execution model. Instead of requiring a traditional compiler pipeline to be part of the language specification, GTL uses an open-source syntax checker and an open-source converter.

GTL Source Code ↓ Open-Source Syntax Checker ↓ Open-Source Converter ↓ GTL Execution Environment

Bootable GTL Environment

A minimal GTL bootable image can contain a small operating environment written in C. GTL source files are placed inside the SC directory of the image. 

GTL IMAGE
│
├── Boot
│
├── System
│
└── SC
    ├── program1.gtl
    ├── program2.gtl
    ├── system.gtl
    └── ...

When the environment starts, it can locate the source files in SC, pass them through the GTL syntax checker, and then use the GTL converter to prepare them for execution.

Open-source tooling: The syntax checker and converter are intended to be open source, allowing developers to inspect, modify, and build their own GTL tooling.

Complete Example

The following example demonstrates the intended style of a GTL program using input, variables, calculations, type checking, conditions, and output. 

uselib gteamtools as gt

code calculator do

    var make "first"
    var make "second"

    var set val "first" by
        gt.basicinput("Input first number: ")

    var set val "second" by
        gt.basicinput("Input second number: ")

    if type(var "first") == int
       |and|
       type(var "second") == int then

        var make "output"

        var "output" cal add "first", "second"

        output(var "output")

    else do

        output(
            "Invalid kind of input. Please input a value."
        )

    end

end

Design Philosophy

GTL is intended to be recognizable as its own language rather than simply being another implementation of an existing language.

  • Simple enough for normal application development.
  • Powerful enough for hardware and firmware.
  • Capable of system-level programming.
  • Portable across different architectures.
  • Integrated with the GTeam ecosystem.
  • Flexible enough to support both high-level and low-level code.
  • Open-source tooling around the language.
The long-term goal: GTL should be able to scale from a tiny microcontroller program all the way up to major parts of GTeam OS.
